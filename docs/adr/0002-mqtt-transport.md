# ADR-0002. MQTT для обміну телеметрією та командами

## Контекст

Контролер або емулятор передає S-01…S-11, heartbeat і результати виконання команд. Сервер передає цільові кути й режими. Потрібно підтримувати 1–10 емуляторів, ідентифікувати повторні доставки та не виконувати застарілі команди після відновлення зв’язку.

Рішення стосується ділянки «контролер / емулятор — сервер». Підстави: FR-01…FR-03, FR-07, FR-08, NFR-03…NFR-06 у [requirements.md](../requirements.md).

## Варіанти

| Варіант | Переваги для проєкту | Обмеження |
|---|---|---|
| MQTT через брокер | Обмін за темами; окремі потоки пристроїв; узгоджується з поточною архітектурою | Окремий процес брокера; потрібні права тем і оброблення повторів |
| HTTP-запити між контролером і сервером | Єдиний підхід із серверним API | Для команд до контролера потрібне опитування або додатковий канал |
| Власний протокол поверх TCP | Повний контроль формату обміну | Потрібно самостійно визначати кадрування, підтвердження, повтори та відновлення з’єднання |

## Рішення

Обрано MQTT через локальний брокер для телеметрії, подій, heartbeat, команд і результатів. `DataCollection` публікує дані, `ResourceAccess` приймає їх і передає до `DataQuality`; `DeviceControl` отримує дозволені команди та повертає результати.

Простір тем розділяється за манекеном: `dt/{device_id}/telemetry`, `/events`, `/heartbeat`, `/commands`, `/results`. Це проєктний контракт, який потрібно реалізувати однаково на контролері та сервері.

- Для телеметрії, подій, команд і результатів прийнято **QoS 1**. Він допускає повторні доставки, тому відліки, події та команди мають прикладні ID. MQTT-підтвердження не означає запису в БД або завершення фізичного руху.
- Повторний ID команди не запускає рух удруге: контролер повертає відомий статус. Команда також містить строк чинності та ідентифікатор поточного сеансу керування. Після перезапуску або втрати зв’язку старий сеанс недійсний; новий відкривається після синхронізації та явного дозволу роботи.
- Команди передаються з `retain=false`; їх накопичення для відключеного контролера не допускається. Контролер додатково відхиляє прострочені команди й команди попереднього сеансу. Відновлення мережі не відновлює рух.
- Heartbeat надсилається раз на 1 с; після 3 с без нього сервер позначає дані неактуальними та блокує нові команди руху. Після підключення запитується поточний стан усіх 11 сигналів із ціллю до 5 с за NFR-05.
- Аварійні події під час розриву зв’язку накопичуються локально та передаються повторно до прикладного підтвердження збереження. Історична подія потрапляє в журнал, але не замінює новіший поточний стан.
- Облікові дані й права MQTT-тем обмежують кожний контролер власним пристроєм. UI працює через серверний API; право керування перевіряє сервер за NFR-06.

Для UI базовим сценарієм залишається опитування API кожні 200 мс. WebSocket залишається альтернативою для перевірки Г-01 у [latency.md](../latency.md), а не вже підтвердженим покращенням.

## Наслідки

- Новий емулятор додається з окремим `device_id` без зміни загального маршруту даних.
- Брокер стає спільною точкою залежності. При його недоступності локальні обмеження руху й аварійне блокування продовжують діяти.
- Потрібні дедуплікація, правила сеансів, локальний буфер подій і контроль його заповнення. 
- Додаткові ID та службові поля збільшують фактичний обсяг повідомлень: оцінка 16 байт у requirements.md залишається моделлю логічного запису.
- Перевірка включає повторну доставку відліку й команди, відключення брокера, заборону старої команди після підключення, повноту журналу та прогони NFR-03…NFR-06.
